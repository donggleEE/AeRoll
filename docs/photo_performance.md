# 촬영 후처리 지연 측정과 최적화

## 확인한 원인과 변경

수정 전부터 `CameraSession`은 원본 바이트를 읽은 뒤 셔터를 다시 열고, 최대 3장의 직렬 저장 큐와 영구 `PhotoProcessor` isolate를 사용했다. 따라서 저장 완료까지 기다리는 현상을 모두 셔터 잠금이나 UI isolate의 필터 연산 탓으로 볼 수는 없었다.

주요 비용은 JPEG 디코딩·인코딩과 전체 사진을 복사하면서 수행하던 픽셀 순회였다. `image.bakeOrientation`은 방향 변경이 없어도 복사했고, 같은 크기 크롭과 필터 출력 변환도 전체 버퍼를 복사했다. 원본·강도 0%에서도 필터 API가 이미지를 복제했다. 라이브 미리보기는 카메라 Texture/GPU 경로이고 사진은 고해상도 JPEG/CPU 경로다. 같은 사진에 필터를 두 번 적용하는 구조는 아니었다.

- 방향 변경·크롭이 없을 때 원본 디코딩 버퍼를 그대로 사용한다.
- worker가 소유한 8비트 RGB/RGBA 버퍼를 직접 처리한다. 외부용 `applyToImage`는 원본 불변 계약을 유지한다.
- 필터/강도별 LUT를 각 필터 최대 8개로 제한해 재사용하고, JPEG 품질 95 인코더의 테이블도 재사용한다. 픽셀 계산식·최종 반올림은 바꾸지 않았다.
- 원본과 강도 0%는 필터 순회를 건너뛴다. 크롭·방향과 기존 JPEG 출력 결과를 유지하기 위해 무조건 입력 JPEG를 그대로 저장하는 최적화는 적용하지 않았다.
- isolate 메시지는 `TransferableTypedData`를 사용한다. 입력 포장에는 작은 바이트 복사가 남으므로 `transferIn`으로 별도 계측한다. 디코딩·리사이즈·필터·인코딩은 주 isolate에서 실행하지 않는다.
- 처리된 동일 이미지에서 최대 변 120픽셀 썸네일을 worker가 생성한다. 최종 저장에는 여전히 전체 해상도 JPEG95를 사용한다. 기존 UI도 `cacheWidth: 120`을 사용했으므로 과거 UI가 무조건 전체 해상도를 디코딩했다고 단정하지 않는다.
- 촬영 직후 90ms 피드백을 유지하고 갤러리 버튼의 작은 진행 표시로 처리 중임을 나타낸다. 기기 앨범 저장이 끝난 뒤에만 실제 결과·썸네일을 표시하며 하단 완료 텍스트는 추가하지 않았다.
- 미리보기 GPU 결과를 캡처해 저장하거나 검증되지 않은 GPU 사진 처리로 교체하지 않았다. 디코딩·인코딩이 주 비용으로 남고, 기존 색/출력 일치가 확인된 CPU 경로를 최적화했다.

## 동일 Windows 입력의 전후 비교

같은 Windows 호스트, Dart JIT, 4000×3000 JPEG 2,302,973바이트, JPEG95, 4:3, cold 강도 50%를 사용했다. 입력 생성은 측정 전에 별도로 끝냈고, 전후를 별도 프로세스에서 순차 실행했다. 각 조건은 한 번 예열 후 3회 측정한 중앙값이다. 변경 후에는 작은 썸네일 생성 비용도 포함한다. 아래 값은 실기기 센서·MediaStore 시간을 포함하지 않는다.

| 조건 | 변경 전 전체 후처리 | 변경 후 전체 후처리 | 관측 변화 |
|---|---:|---:|---:|
| 원본, 1배 | 1,023.91ms | 977.34ms | 약 4.5% 감소 |
| cold 50%, 1배 | 1,567.14ms | 1,079.62ms | 약 31.1% 감소 |
| cold 50%, 디지털 3배 | 1,957.97ms | 1,424.73ms | 약 27.2% 감소 |

단계별 중앙값은 다음과 같다. 각 단계의 중앙값 합계와 총시간 중앙값은 일치하지 않을 수 있다.

| 단계 | cold 1배 전 | cold 1배 후 | cold 3배 전 | cold 3배 후 |
|---|---:|---:|---:|---:|
| 디코딩·JPEG 색상 변환 | 567.76ms | 487.63ms | 519.79ms | 496.91ms |
| 방향 보정 | 4.80ms | 0.008ms | 4.98ms | 0.009ms |
| 크롭·리사이즈 | 9.44ms | 0.010ms | 275.51ms | 263.48ms |
| 필터·강도 | 428.33ms | 60.91ms | 547.56ms | 60.44ms |
| 작은 썸네일 생성 | 별도 UI 경로 | 1.59ms | 별도 UI 경로 | 1.67ms |
| JPEG95 인코딩 | 541.45ms | 526.79ms | 598.93ms | 598.24ms |

1배 조건은 방향·크롭이 실제로 필요 없는 입력이다. 디코더 구현은 교체하지 않았으므로 해당 단계의 시간 차이에는 실행 변동·메모리/GC 영향이 포함된다. 핵심 개선은 필터 순회와 불필요한 복사 제거이며, 남은 주요 비용은 디코딩·인코딩이다. 실제 기기의 개선율로 일반화하지 않는다.

같은 측정 프로세스의 최대 RSS는 1배 묶음에서 485,109,760 → 392,986,624바이트(약 463 → 375MiB), 3배 묶음에서 524,599,296 → 414,896,128바이트였다. JIT·런타임을 포함한 프로세스 수치이며 사진 버퍼만의 메모리나 Android/iOS 메모리 수치가 아니다.

재현 명령:

```sh
dart run tool/photo_latency_benchmark.dart prepare
dart run tool/photo_latency_benchmark.dart before
dart run tool/photo_latency_benchmark.dart after
dart run tool/photo_latency_benchmark.dart before zoom
dart run tool/photo_latency_benchmark.dart after zoom
```

결과는 `build/photo_latency_before.json`, `photo_latency_after.json` 및 각각의 `_zoom.json` 파일에 저장된다. 이전 경로는 `test/support/legacy_photo_pipeline.dart`에 보존했다.

## 캡처·저장·UI 단계 계측

`CameraSession.photoTimings`에서 최근 20개 작업의 마이크로초 단위 계측을 조회할 수 있다. 고해상도 버퍼나 개인 사진 경로를 계측 기록에 보관하지 않는다.

| 항목 | 의미 |
|---|---|
| `inputToRequest`, `cameraWait` | 입력 피드백 이후 요청 진입 및 기존 줌/초점/플래시 명령 대기 |
| `sensorCapture`, `captureComplete` | `takePicture` 소요 및 입력 이후 플랫폼 캡처 반환 시점 |
| `sourceRead`, `captureReady` | 원본 바이트 읽기 및 센서 취득 잠금 해제 시점 |
| `nextCaptureAvailable` | 실제 `canCapture`가 다시 참인 시점. 세 장 큐가 차거나 카메라가 중지되면 센서 준비와 다르다 |
| `sourceBackup`, `backupAwait`, `queueWait` | 원본 영구 보관 I/O, 그 완료를 기다린 시간, 직렬 처리 대기 |
| `transferIn`, `transferOut`, `workerRoundTrip` | isolate 입력 포장·출력 포장 및 전체 왕복 |
| `decode`, `orientation`, `cropResize`, `filter`, `encode` | worker의 디코딩·방향·크롭/확대·필터/강도·최종 인코딩 |
| `thumbnail` | 같은 처리 이미지에서 작은 썸네일 생성 |
| `fileWrite`, `metadataPrepare`, `albumSave`, `metadataCommit` | 앱 파일, 준비 메타데이터, 앨범 API, 최종 메타데이터 |
| `totalSaved`, `cleanup`, `completion` | 실제 저장 단계 완료, 원본 정리, 호출자 완료 |
| `thumbnailPresented`, `savedToThumbnail` | 썸네일 첫 프레임 후 UI 콜백 시점 및 저장 이후 지연. 카메라 화면이 없으면 측정되지 않는다 |

`decode`에는 JPEG 디코더의 색상/포맷 변환이 포함된다. 별도의 ICC→sRGB 변환은 이전과 마찬가지로 지원하지 않는다. JPEG의 일반 8비트 RGB 경로에서는 필터용 추가 전체 포맷 변환이 필요 없다. 일반 포맷의 변환은 필터 단계에 포함한다.

수동 통합 측정은 다음 명령으로 실행했다.

```sh
flutter test --no-pub tool/photo_session_benchmark_test.dart
```

실제 `PhotoProcessor`와 파일 I/O를 사용한 12MP 세 장 연속 시험에서 세 장이 모두 저장됐고, 카메라를 중지한 뒤에도 큐가 완료됐다. 주 isolate의 10ms 타이머는 311회 응답했고 최대 간격은 23.19ms였다. 이는 UI 이벤트 루프가 0.4~0.5초의 디코딩/인코딩 동안 통째로 멈추지 않았다는 확인이며 카메라 FPS 검증은 아니다.

이 시험의 센서는 파일 복사 대역이고 앨범도 파일 복사 대역이다. 관측된 캡처 반환 5.00~9.55ms, 원본 확보·센서 잠금 해제 16.92~26.83ms, 영구 원본 쓰기 15.76~19.57ms, 앱 파일 쓰기 6.35~8.91ms, 앨범 대역 복사 3.61~5.07ms는 실제 기기 수치가 아니다. 세 장 저장 시점은 각각 입력 후 약 1.14·2.07·3.16초였고 뒤 작업의 직렬 대기가 포함된다. 세 번째 입력 뒤에는 큐 상한 때문에 추가 촬영을 제한했다. 결과는 `build/photo_session_profile.json`에 보관했다. 이전 실기기 캡처 지연과의 수치 비교는 수행하지 못했다.

## 원본 보존과 정확도

원본을 읽은 뒤 후처리 완료를 기다리지 않고 셔터를 다시 연다. 원본 영구 기록은 앞 사진의 CPU 작업과 겹쳐 실행하며, 디코딩된 큰 사진은 한 장씩 처리한다. 촬영·재시도 합계 최대 3개, LUT 각 필터 최대 8개, 계측 20개와 작은 최신 썸네일 하나로 메모리를 제한한다.

`aeroll_photo_jobs`에 원본과 필터·강도·배율·반전·비율·방향·촬영 시각을 고정해서 기록한다. 기록이 완료된 뒤 카메라 임시 파일을 정리한다. 저장 실패 시 이 원본과 준비된 최종 JPEG/메타데이터를 남기고, 상단 재시도 아이콘을 제공한다. 재시작 후에도 해당 작업을 찾으며 이미 인코딩한 JPEG가 있으면 다시 처리하지 않는다. 완료 ID가 있으면 앨범 호출도 반복하지 않는다. 사진 완료 전에는 성공 목록이나 완료 썸네일로 표시하지 않는다.

화면 이동·일반적인 백그라운드 전환·dispose 시 확보한 작업을 마저 처리하도록 기존 수명주기를 유지했다. Flutter isolate는 OS의 무제한 백그라운드 실행 보장이 아니다. 프로세스가 중단되면 완료된 영구 원본 작업을 다음 실행에서 재시도할 수 있다. 영구 보관 자체가 실패하면 임시 원본을 지우지 않고 앱을 닫지 말고 재시도하도록 안내한다. 기록 전 강제 종료·디스크 오류·OS 임시 파일 정리까지 보존을 보장하지 않는다. 앨범 API와 로컬 저널은 단일 트랜잭션이 아니므로 호출 직후 OS가 종료되는 극히 좁은 구간의 정확히 한 번 저장도 보장하지 않는다.

방향 1·2·6·8, 전면 반전, 비율 크롭, 디지털 확대, 원본/warm/cold, 강도 0·50·100%의 72개 JPEG/PNG 조합에서 이전 경로와 바이트가 일치했다. 썸네일 생성 전후의 최종 파일도 같았다. 해상도·JPEG 품질95·EXIF/ICC의 기존 보존 방식과 필터 수식을 유지한다. 복구·실패·재시작·중복 완료 방지, 기존 3장 큐와 화면 회귀도 자동 테스트로 확인했다.

실제 Android/iOS 센서 캡처·다음 촬영 시각·기기 앨범·미리보기 프레임·발열·장시간 연속 촬영 메모리와 iOS 실행은 연결 기기가 없어 미검증이다. 위 Windows CPU/파일 대역 결과를 해당 검증으로 대신하지 않는다.
