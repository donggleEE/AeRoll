# 카메라·필터·갤러리 구현 계획

최신 작업은 이 문서 마지막의 **전체 화면 카메라와 촬영 응답성 개선** 절을 따른다. 앞부분은 최초 구현의 계약과 검증 이력이며, 최신 비율·에셋 계약이 우선한다.

## 목표와 확인한 상태

- 이번 범위는 카메라 촬영, 제공된 투명 PNG 필터 적용, 기기 앨범 저장, 앱 갤러리 및 사진 상세 조회다.
- 시작 시 `lib/main.dart`와 `test/widget_test.dart`는 Flutter 기본 카운터 데모였다.
- 제공된 `assets/images/filter/example.png`는 700×840, 8비트 RGBA PNG다. 라이트리크 질감이며 메인 에이전트 확인 결과 알파 범위는 0~92다. 색상 LUT가 아닌 투명 이미지 합성으로 사용한다.
- 기존 프로젝트 목적과 관계없는 문서는 변경하지 않는다. 서버와 계정 기능은 이번 범위에 포함하지 않는다.

## 역할과 파일 소유권

| 역할 | 작업 | 수정 범위 | 완료 기준 |
|---|---|---|---|
| project_manager | 작업 분해, 인터페이스와 할당, 현황 및 기록 정리 | 이 문서, `docs/command_history.md` | 두 구현 역할의 연동 계약과 검증 기준 전달 |
| backend | 카메라 수명주기, 필터 합성, 실제 앨범 저장, 앱 사진 저장소 | `lib/models/`, `lib/services/`, `lib/controllers/`, `pubspec.yaml`, `pubspec.lock`, 필요한 Android/iOS 설정 | 선택 필터가 최종 파일에 반영되고 저장 후 재조회 가능 |
| frontend | 카메라, 필터 선택, 강도 조절, 촬영 피드백, 갤러리와 상세 UI | `lib/main.dart`, `lib/screens/`, `lib/widgets/`, `lib/theme/` | 서비스에 연결된 화면 흐름과 오류·빈 상태 제공 |
| tester | 분석, 테스트, 관련 빌드 검사 및 결과 보고 | `test/`, 필요한 테스트 보고서 | 성공과 실패, 미실행 실기기 검증을 구분해 메인에 보고 |

구현 역할은 서로 소유한 파일을 임의로 수정하지 않는다. 인터페이스 변경은 상대 역할과 메인에게 알린다. `pub get`과 의존성 변경은 backend가 먼저 수행하고 tester가 최종 검사한다.

## 인터페이스 계약

### 모델

- `lib/models/film_filter.dart`: `FilmFilter`는 `id`, `name`, nullable `assetPath`를 제공한다. `filmFilters`는 원본과 제공 PNG 필터의 상수 목록이다. 원본의 `assetPath`는 null이다.
- `lib/models/saved_photo.dart`: `SavedPhoto`는 `id`, 앱 내부 이미지의 `path`, `createdAt`, `filterName`을 제공한다. 갤러리는 실제로 읽을 수 있는 앱 사본을 사용한다.

### 저장소

- `lib/services/photo_repository.dart`: `PhotoRepository`는 `Future<List<SavedPhoto>> listPhotos()`를 제공한다.
- 실제 구현은 앱 사본과 메타데이터를 영구 보관하고 최근 촬영순으로 반환한다. 기기 앨범 내 실제 사진과 앱 사본은 구분하며, 앨범 저장 실패를 성공으로 반환하지 않는다.
- 앱 갤러리는 앱 사본을 조회하므로 기기 앨범에서 사진을 삭제해도 앱 사본은 별도로 남는다. 이 차이를 사용자 안내와 최종 보고에서 명시한다.

### 카메라 제어

- `lib/controllers/camera_session.dart`: `CameraSession extends ChangeNotifier`.
- 생성자: `CameraSession({PhotoRepository? repository})`; 저장소 접근자: `PhotoRepository get repository`. 구현에는 테스트를 위한 카메라 로더·컨트롤러 생성·플랫폼 지원 여부 주입도 추가되었다.
- 상태: `CameraController? get cameraController`, `bool get isInitializing`, `bool get isCapturing`, `String? get errorMessage`.
- 동작: `Future<void> initialize()`, `Future<SavedPhoto> capture({required FilmFilter filter, required double intensity})`, `Future<void> suspend()`, `Future<void> resume()`, `dispose()`.
- 캡처 실패는 예외와 `errorMessage`로 전달하고 진행 상태를 복구한다. 중복 촬영 요청은 거부한다. 프런트엔드는 반환 결과 확인 후 저장 성공을 안내한다.
- 프런트엔드가 앱 수명주기를 감시해 `suspend()`와 `resume()`를 호출한다. backend는 요청 경합과 자원 해제를 안전하게 처리한다.

### 미리보기와 저장의 동일 합성

- 촬영 영역은 이미지 비율에 맞춘 세로 5:6이다. 원본을 방향 보정한 뒤 중앙에서 `BoxFit.cover`에 해당하는 방식으로 잘라 사용한다.
- PNG 역시 같은 영역을 `cover`로 채우고 원래 알파에 선택 강도를 곱해 source-over 합성한다. 기본 강도는 1.0이며 0~1 범위로 제한한다.
- 프런트엔드는 같은 5:6 영역에서 카메라 원본을 중앙 cover로 표시하고 선택 PNG를 `Image.asset(fit: BoxFit.cover)`와 강도로 겹친다.
- backend는 촬영 순간 필터와 강도를 고정한다. 원본 필터에서는 PNG를 합성하지 않는다.
- 실제 카메라의 방향·미리보기 크기·전면 반전 차이는 기기별로 확인한다. 필요하면 공통 계산 함수를 합의해 사용한다.

## 검증 기준과 남은 위험

backend는 로직 구현, frontend는 화면 연동과 파일 포맷을 완료했다. tester는 최종 통합 분석, 자동 테스트 16건과 Android 디버그 APK 빌드 통과를 보고했다. 실제 기기 촬영과 앨범 저장 확인은 아직 완료되지 않았다.

- 원본과 필터를 전환하고 투명 PNG 질감이 미리보기와 최종 사진에 반영되는지 확인한다.
- 강도 변경, 촬영 중 중복 요청 방지, 실패 후 상태 복구를 확인한다.
- 기기 앨범 저장과 앱 재시작 후 갤러리 조회를 각각 확인한다.
- 권한 거부, 사진 없음, 읽기 및 저장 실패, 앱 백그라운드 전환과 복귀를 확인한다.
- tester는 `dart format`, `flutter analyze`, `flutter test`와 가능한 Android 빌드 결과를 보고한다.
- 자동 테스트 성공만으로 실기기 카메라, 이미지 방향과 앨범 저장 검증을 완료 처리하지 않는다. Windows에서는 iOS 빌드와 실기기 검증이 제한될 수 있다.
- `.codex/agents/`의 모델 설정은 요청대로 유지하되 이번 실행 도구가 `gpt-5.5` 선택을 제공하지 않으므로 실제 팀 실행 모델은 상위 세션을 상속한다.
- 기기 앨범 저장 성공 후 앱 메타데이터 확정이 실패하면 부분 저장 상태가 발생할 수 있다. 구현은 사본을 보존하고 명시적 오류를 전달하므로 단순 성공으로 숨기지 않는다.

## 통합 검증 중 발견 사항

- `flutter analyze --no-pub`는 문제 없음으로 통과했다.
- 최초 전체 테스트 16건 중 15건은 통과하고 갤러리 재시도 1건은 실패했다. 원인은 갤러리 `_reload`의 `setState` 콜백이 Future를 반환하는 assertion이었다. frontend가 동기 블록 콜백으로 수정한 뒤 tester가 전체 16건 통과를 확인했다.
- 최종 정적 분석과 자동 테스트는 통과했다. 구성은 이미지 합성 4건, 사진 저장소 3건, 카메라 세션 4건, 화면 상호작용 5건이다.
- 자세한 테스트 범위, 발견 결함과 실행 결과는 `docs/test_report.md`에 기록한다.
- 모바일 기기는 연결되지 않았다. 개발 환경 검사에서 일부 Android 라이선스 경고가 있었으나 실제 빌드에서는 이미 수락된 라이선스로 Android SDK Platform 35가 자동 설치되어 라이선스 차단은 확인되지 않았다.
- 최초 Android 디버그 빌드는 앱의 `WRITE_EXTERNAL_STORAGE` 최대 SDK 29와 camera 플러그인의 28이 충돌해 매니페스트 병합에서 실패했다. backend는 tools 네임스페이스와 `tools:replace="android:maxSdkVersion"`를 추가해 앱의 API 29 범위를 유지하도록 수정했다. 이후 tester의 재빌드는 138.7초 만에 성공했고 `build/app/outputs/flutter-apk/app-debug.apk`를 생성했다.
- 테스트 화면 이미지는 Ahem 테스트 글꼴을 사용하므로 레이아웃 확인 근거로만 사용한다. 실제 기기 글꼴 가독성, 미리보기와 저장 사진의 방향 및 색감은 별도 확인이 필요하다.

## 전체 화면 카메라와 촬영 응답성 개선

### 요청과 확인한 자료

- 전후면 카메라 전환, 새 필름 이미지 경로 반영, 예시 사진에 각 필름을 적용한 썸네일 선택 버튼을 구현한다.
- 참고 화면의 전체 사진 위 격자, 하단 반투명 필터 목록, 큰 흰색 촬영 버튼, 왼쪽 갤러리와 오른쪽 카메라 전환 배치를 따른다.
- 실제 에셋은 `assets/images/filter/light.png`, `assets/images/filter/cold.png`이며 `assets/filter/`가 아니다. 이전 `example.png`는 존재하지 않는다.
- 공통 예시 사진은 `assets/images/example/example_image.jpg`다. 메인 확인 결과 예시 사진은 1180×842 RGB, 두 PNG는 700×840이며 알파 범위는 light 0~92, cold 5~90이다.
- 촬영 대기를 줄이되 실제 저장 완료 전 저장 성공을 표시하지 않는다.

### 확정 인터페이스와 표시 계약

- `CameraSession`은 `canSwitchCamera`, `isSwitchingCamera`, `isFrontCamera`, `canCapture`와 `pendingSaves`를 제공하고 `Future<void> switchCamera()`를 추가한다.
- `capture`는 선택 인자 `double frameAspectRatio = 5 / 6`을 받는다. 기본값은 기존 호출 호환용이고 새 UI는 실제 전체 화면 사진 영역의 너비/높이 비율을 전달한다.
- `isCapturing`은 `takePicture`와 원본 바이트 취득 동안만 true다. 취득이 끝나면 다음 촬영이 가능하지만 큐 상한과 다른 카메라 상태를 함께 반영한 `canCapture`로 버튼 활성화를 결정한다.
- `capture`의 `Future<SavedPhoto>`는 실제 합성과 기기 앨범 저장 완료 후 완료된다. 각 Future의 오류를 처리하고 취득 피드백과 저장 성공 안내를 구분한다.
- UI는 이번 참고 화면에 맞춰 강도를 1로 고정하고 이전 슬라이더를 제거했다. 촬영 시 햅틱과 90ms 플래시를 제공하며 저장 성공 안내는 각 Future가 완료된 뒤에만 표시한다.
- `pendingSaves`는 취득한 뒤 저장 중인 작업 수를 뜻한다. 센서 취득까지 포함한 미완료 사진은 최대 3장으로 제한하고 이미지 합성·저장은 직렬 처리한다. 단순히 무제한 Future를 시작하는 방식으로 속도를 개선하지 않는다.
- 저장 대기 중 렌즈 전환은 허용하되 센서 취득이나 초기화·다른 전환 중에는 거부한다. 선택 렌즈는 백그라운드 복귀에도 유지한다.
- 전면 미리보기의 기본 거울 표시와 저장을 맞추기 위해 전면 사진은 필터 합성 전에 수평 반전한다. 실제 플러그인 방향·거울 동작은 실기기 확인이 필요하다.
- 필름 목록은 원본, light, cold이며 예시 이미지 경로 상수를 필터 모델에서 제공한다. 선택 버튼은 예시 사진 위에 해당 PNG를 원래 알파로 합성한다. 썸네일은 1:1 영역을 사용할 수 있다.

### 전체 화면 구도와 속도 기준

- 이전 5:6 저장을 유지한 채 화면만 확대하면 저장 사진과 보이는 구도가 달라진다. 메인은 전체 화면 요구를 우선해 출력 비율도 실제 뷰포트 비율로 바꾸도록 결정했다.
- 사진 원본을 해당 비율로 중앙 자르고 PNG 역시 같은 영역에 cover로 합성한다. 격자와 조작 UI는 저장 사진에 포함하지 않는다.
- 촬영 시 필터·강도·비율·렌즈 정보를 고정하고 저장 중 설정을 바꿔도 기존 작업의 결과를 바꾸지 않는다.
- backend는 `lib/services/photo_processor.dart`에 영구 이미지 처리 isolate와 두 PNG의 디코딩 캐시를 구현하고 초기화 시 미리 준비하되 화면 진입을 막지 않도록 구성했다. 큐 상한, 처리 완료 후 메모리 해제와 앱 종료·취득 경합을 함께 검증한다.
- 측정용 `lastCaptureDuration`은 센서 촬영과 바이트 취득 시간, `lastSaveDuration`은 합성과 저장 시간을 구분해 제공한다. 실제 측정값을 확인하기 전 지연 제거를 단정하지 않는다.
- 빠른 취득 피드백은 실제 기기 지연을 제거했다는 뜻이 아니다. 성능 개선은 구조 변경과 실기기 측정을 구분해 보고한다.

### 완료 검증과 위험

- 전후면 전환 후 촬영, 전환 불가 기기, 촬영 중 전환 요청, 앱 복귀 렌즈 유지와 dispose 경합을 검사한다.
- 여러 촬영의 순서, 최대 3장 제한, 필터·강도·렌즈 고정, 저장 실패 후 큐 회복과 각 Future의 오류 처리를 검사한다.
- 새 에셋 로딩, 서로 다른 필름 썸네일, 선택 표시, 전체 화면 비율의 저장 결과와 격자 비저장 여부를 검사한다.
- 이전 검증 16건과 APK 성공은 이번 변경의 완료 근거로 재사용하지 않는다. 새 최종 결과는 tester 보고 후 갱신한다.
- 실제 카메라 지연, 전면 반전, 미리보기와 저장 구도·색감, 기기 앨범 및 iOS는 실기기 검증 여부를 구분한다.

### 구현 보고와 검증 대기 상태

- backend는 기존 모델·카메라 제어·합성 코드 및 에셋 등록을 수정하고 `photo_processor.dart`를 추가했다. `flutter pub get`, 관련 파일 포맷과 backend 정적 분석 통과를 보고했다.
- frontend는 `camera_screen.dart`, `camera_viewfinder.dart`, `film_filter_selector.dart` 세 파일만 수정했다. 전체 화면 미리보기와 3×3 격자, 28% 검정 반투명 패널, 흰색 선택 라벨의 굵은 검정 글자, 필름 적용 썸네일, 큰 흰색 촬영 버튼과 갤러리·전환 버튼을 구성했다.
- frontend는 0 크기 방어와 방향 잠금 순서를 유지했고 관련 파일 포맷 및 화면 영역 정적 분석 통과를 보고했다.
- 이전 기본 구현 검증 16건과 이후 0 크기 시작 화면 회귀 수정의 17건 통과는 과거 이력이다. 이번 변경은 tester의 새 실행에서 정적 분석 문제 없음, 자동 테스트 24건 모두 통과, Android 디버그 APK 빌드 성공을 확인했다.
- 이번 최종 분석은 13.8초, 자동 테스트 실행은 약 3초, APK 빌드는 28.1초였다. APK 크기는 187,681,206바이트이며 이 시간은 실제 촬영 지연 측정값이 아니다.
- 테스트 파일 포맷 검사는 9파일에서 변경 없음으로 통과했다. 초기 테스트의 미종료 타이머는 화면 안정화 대기를 추가해 해결했으며 운영 코드의 새 결함으로 보고하지 않았다.
- 최종 APK의 에뮬레이터 설치·카메라 전환·촬영 확인은 메인 에이전트가 진행한다. 실제 휴대폰 성능과 iOS 검증을 대체하지 않는다.
- 메인의 화면 검토 후 frontend가 하단 조작부를 더 작게 조정했다. 썸네일 높이 82→56, 너비 66→52, 촬영 버튼 84→72로 줄이고 흰 필터 라벨은 패널 위에 분리했다. 360×640 기준 패널은 높이 156, 하단 안전 여백 34가 있으면 180이다. 패널 검정 알파 28%는 유지한다. 관련 포맷과 분석 및 아래 추가 회귀 검증을 통과했다.
- 축소 후 최종 재검증은 분석 문제 없음(4.6초), 자동 테스트 25건 모두 통과(약 3초), Android APK 빌드 성공(25.6초)이다. 새 회귀 1건은 360×640의 하단 안전 여백 0·34에서 패널 높이가 화면의 1/3보다 작고 알파 28%임을 확인한다. 24건 통과는 축소 전 이력이며 현재 최종 수는 25건이다.

### 메인 에이전트의 에뮬레이터 확인

- 기존 에뮬레이터는 메모리 부족 종료와 저장 공간 부족 설치 실패가 발생했다. 이후 메모리 4GB 및 별도 QA userdata 이미지로 실행 환경을 구성했다. 초기 설치 실패 후 Flutter의 자동 앱 제거·재설치 시도가 있었으므로 기존 테스트 앱 내부 데이터 보존은 보장할 수 없다. AVD 전체 초기화는 수행하지 않았다. 이 환경 문제를 Flutter 예외나 앱 결함으로 단정하지 않는다.
- 최종 화면 `build/camera_ui_final.png`는 720×1280이며 하단 패널 높이는 약 26.6%였다. 라벨의 패널 위 분리, 실제 예시 사진과 필름 합성 썸네일 3종, 실행 중 예외 없음을 확인했다.
- 하단 축소 이전의 동일 backend로 전면·후면 전환을 각각 1회 확인했다. 콜드 필터 사진이 MediaStore에 720×1280으로 저장되고 앱 썸네일에도 표시됨을 확인했다.
- 해당 디버그 에뮬레이터의 1회 측정은 센서 취득 2.513초, 합성과 저장 7.339초였다. 즉시 완료를 보장하는 결과가 아니며 취득 후 UI 잠금을 풀고 저장을 백그라운드로 분리한 구조가 개선 사항이다. 실제 휴대폰 측정값은 아니다.
- 최종 축소 APK에서 첫 사진의 저장 대기 수가 1인 동안 추가 촬영을 수행했다. MediaStore ID 38과 39로 두 사진이 모두 720×1280으로 저장되었고 앱 갤러리에는 최종 4장이 표시되었다. `build/gallery_final.png`를 확인했으며 Flutter 오류 로그는 없었다.
- 워밍 후 추가 촬영의 디버그 에뮬레이터 측정은 센서 1.566초, 합성과 저장 3.772초였다. 초기 2.513초·7.339초와 함께 환경 참고값으로만 보고하며 물리 기기의 속도 보장으로 사용하지 않는다.
- QA용 분리 ABI APK에서 일반 APK로 바꿀 때도 versionCode 4001→1에 따른 재설치로 별도 QA 이미지의 앱 사본이 초기화되었다. 이후 최종 앱에서 촬영·저장을 다시 검증했다.
- 이번 자동 검사·Android 빌드·에뮬레이터 검증은 완료했다. 실제 휴대폰의 카메라 구도와 색감, 저메모리 성능, 권한 거부 및 iOS 동작은 별도 실기기 확인이 남아 있다.
