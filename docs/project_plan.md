# 카메라·필터·갤러리 구현 계획

최신 작업은 아래 **촬영 후처리 지연 최적화** 절을 따른다. 나머지는 이전 구현의 계약과 검증 이력이며 최신 계약이 우선한다.

## 2026년 11월 4일 촬영 후처리 지연 최적화

- 촬영부터 처리·저장·썸네일까지 단계별 계측을 추가했다. 기존 전용 isolate와 3장 직렬 큐, 원본 확보 후 셔터 재활성화는 유지했다.
- 방향·크롭이 불필요한 경우의 전체 이미지 복사를 제거하고 worker 소유 8비트 버퍼를 직접 처리한다. 제한된 LUT 캐시·JPEG95 인코더 재사용·전달 가능한 바이트 버퍼와 작은 썸네일을 사용한다. 원본과 0%는 필터 순회를 생략한다.
- `photo_capture_store.dart`가 촬영 설정과 원본을 영구 기록한다. 실패한 사진은 완료로 표시하지 않고 상단 재시도 아이콘으로 복구한다. 준비된 JPEG와 완료 ID는 재사용하고 성공 뒤 원본을 정리한다. 일반 백그라운드·화면 종료 시 기존 작업을 마저 처리하며 OS 강제 종료 뒤에는 기록된 원본을 재발견한다.
- Windows 동일 12MP 입력의 중앙값: cold 50% 1배 후처리 1,567→1,080ms, 3배 1,958→1,425ms. 1배 필터 단계 428→61ms. 원본 모드 개선은 1,024→977ms로 작았다. 실제 센서·기기 앨범·모바일 FPS 수치가 아니다.
- 최종 정적 분석 문제 없음, 자동 테스트 101건 통과, 별도 12MP 세 장 파일 I/O·worker 통합 시험 통과, Android APK 빌드 성공(14.1초). 수정 전후 72개 JPEG/PNG 조합의 바이트 일치를 확인했다.
- 변경 범위·측정 재현·단계별 수치와 실제 기기 제한은 [촬영 성능 보고서](photo_performance.md), 최종 검사 목록은 [검증 보고서](test_report.md)에 기록했다. 기존 미커밋 변경은 보존하고 서버·외부 업로드·새 의존성은 추가하지 않았다.

## 2026년 11월 4일 촬영 조작과 필터 강도 확장

- 사용자는 팀 에이전트 작업으로 터치 초점, 촬영 타이머 OFF·3·5·10초, 발광 플래시 ON·OFF, 확대 눈금의 연속 세로 드래그, 사진 저장 완료 하단 안내 제거와 필터 강도 0~100%를 요청했다.
- 초점·플래시와 카메라 수명주기는 카메라 제어 담당, 타이머·좌표·제스처·슬라이더는 화면 담당, 필터의 CPU·미리보기·영상 강도는 이미지 담당이 작업한다. 메인은 통합 검토·기준 JPG 비교·문서·최종 검증을 담당한다. 기존 미커밋 변경을 보존한다.
- 초점은 표시 영역의 크롭·크기·추가 디지털 확대·앱의 추가 반전을 역변환한다. 플러그인이 수행하는 센서 회전을 중복 적용하지 않는다. 버튼·핀치·눈금·강도 조작은 초점 탭과 분리하고 표시만 자연스럽게 숨긴다. 실제 초점의 성공·정확도는 실기기 대상이다.
- 타이머는 기본 OFF이며 카운트다운 동안 선택·중복 촬영을 잠근다. 셔터 재입력, 화면 이동·종료와 백그라운드 전환에 취소한다. 남은 시간을 미리보기 안에 표시한다.
- 플래시는 기본 OFF이며 native 카메라 특성으로 지원 여부를 조회한다. ON은 사진 캡처 시 발광하는 모드이며 torch 모드를 사용하지 않는다. 미지원·조회 실패는 조작을 비활성화하고 촬영 기능은 유지한다.
- 눈금 드래그는 현재 배율에서 손가락의 세로 이동 거리에 따라 연속적으로 조절하고 실제 최소~최대값으로 제한한다. 누르고 있는 동안 숨김을 중단하고 놓은 뒤 기존 2초 숨김을 유지한다. 핀치 줌은 보존한다.
- 필터 강도는 `원본 × (1-강도) + clamp(완전 필터) × 강도`를 마지막 정수화 전에 계산한다. 0%는 원본, 100%는 기존 필터다. cold의 음수 값을 원본과 먼저 섞지 않는다. 원본은 슬라이더를 숨기며 warm·cold의 마지막 값은 현재 화면 세션에서 각각 기억한다.
- 사진 저장 완료 안내만 제거하고 실제 저장·상태와 오류 안내는 유지한다. 기준 이미지와 새 기능 검증의 최종 결과·플랫폼 제한은 [검증 보고서](test_report.md)에 기록한다.
- 최종 구현·검증 완료: 정적 분석 문제 없음, 전체 자동 테스트 93건 통과, Android 디버그 APK 빌드 성공(28.7초). 기준 JPG 비교는 warm RMSE 2.60048, cold 2.47645였다. 실제 초점·발광·Impeller 픽셀·모바일 성능·기기 앨범과 iOS는 별도 검증 대상이다.

## 2026년 11월 4일 고정 RGB 필터 교체

- 사용자의 팀 작업 요청에 따라 사진 처리·수학 테스트, 화면·렌더링 테스트, 네이티브 영상 출력을 분담했다. 기존 미커밋 변경을 유지한다.
- 기존 PNG 필터를 제거하고 기존 선택 위치에 원본·warm·cold를 제공한다. 추가 답변으로 확정된 warm 2개 층, cold 3개 층을 순서대로 Normal 합성한 뒤 고정 회색으로 각각 Multiply·Linear Burn 한다.
- `lib/models/filter_transform.dart`가 모든 상수·순차 double 기준식·정규화 선형계수·최종 정수화·Flutter 행렬을 관리한다. 앱 테마 배경은 연산에 사용하지 않는다. 원본은 회색을 포함한 모든 필터 연산을 건너뛴다.
- 사진의 디코딩→EXIF 방향→전면 반전→중앙 크롭→디지털 줌 순서를 유지하고 RGB 연산을 한 번 수행한다. 영구 isolate와 저장 큐를 유지하며 실제 저장은 기존 JPEG 품질 95를 사용한다. 정확 비교에는 손실 없는 PNG 출력 옵션을 사용한다.
- 라이브 카메라와 썸네일은 동일 정의에서 만든 `FilmFilterEffect` 행렬을 사용한다. 격자·배경은 필터 밖에 둔다. CPU 픽셀 경로가 정확도 기준이며 실제 모바일 Texture·GPU와 JPEG 손실 압축의 픽셀 동일성을 보장하지 않는다.
- 영상은 PNG 경로 대신 같은 Dart 정의의 `rgbTransform` 계수를 전달한다. Android는 Media3 SDR 전기 RGB shader, iOS는 sRGB Core Image 행렬을 사용한다. HDR 필터 출력은 거부하며 영상 색관리·GPU 정밀도·인코딩은 사진 CPU 경로와 구분한다.
- 제공된 기준 JPG 세 장이 없어 기준 이미지 MAE·평균 부호 오차·RMSE 비교는 수행하지 않는다. 계수 자동 보정도 수행하지 않는다.
- 기존 코드에는 일반 ICC→sRGB 변환이 없다. 사진 정확도 검증 기준은 sRGB이며 비sRGB·광색역 입력, iOS 빌드·실제 출력, 모바일 실기기 성능은 별도 확인 대상이다. 이번 요청의 최종 실행 결과는 [테스트 보고서](test_report.md)의 최신 절에 기록한다.

## 목표와 확인한 상태

- 이번 범위는 카메라 촬영, 제공된 투명 PNG 필터 적용, 기기 앨범 저장, 앱 갤러리 및 사진 상세 조회다.
- 시작 시 `lib/main.dart`와 `test/widget_test.dart`는 Flutter 기본 카운터 데모였다.
- 제공된 `assets/images/filter/example.png`는 700×840, 8비트 RGBA PNG다. 라이트리크 질감이며 메인 에이전트 확인 결과 알파 범위는 0~92다. 색상 LUT가 아닌 투명 이미지 합성으로 사용한다.
- 기존 프로젝트 목적과 관계없는 문서는 변경하지 않는다. 서버와 계정 기능은 이번 범위에 포함하지 않는다.

## 인터페이스 계약

### 모델

- `lib/models/film_filter.dart`: `FilmFilter`는 `id`, `name`, nullable `assetPath`를 제공한다. `filmFilters`는 원본과 제공 PNG 필터의 상수 목록이다. 원본의 `assetPath`는 null이다.
- `lib/models/saved_photo.dart`: `SavedPhoto`는 `id`, 앱 내부 이미지의 `path`, `createdAt`, `filterName`을 제공한다. 갤러리는 실제로 읽을 수 있는 앱 사본을 사용한다.

### 저장소

- `lib/services/photo_repository.dart`: `PhotoRepository`는 `Future<List<SavedPhoto>> listPhotos()`를 제공한다.
- 실제 구현은 앱 사본과 메타데이터를 영구 보관하고 최근 촬영순으로 반환한다. 기기 앨범 내 실제 사진과 앱 사본은 구분하며, 앨범 저장 실패를 성공으로 반환하지 않는다.
- 앱 갤러리는 앱 사본을 조회하므로 기기 앨범에서 사진을 삭제해도 앱 사본은 별도로 남는다. 이 차이를 사용자 안내와 최종 보고에서 명시한다.

### 카메라 제어

- `lib/controllers/camera_session.dart`: `CameraSession extends ChangeNotifier`.
- 생성자: `CameraSession({PhotoRepository? repository})`; 저장소 접근자: `PhotoRepository get repository`. 구현에는 테스트를 위한 카메라 로더·컨트롤러 생성·플랫폼 지원 여부 주입도 추가되었다.
- 상태: `CameraController? get cameraController`, `bool get isInitializing`, `bool get isCapturing`, `String? get errorMessage`.
- 동작: `Future<void> initialize()`, `Future<SavedPhoto> capture({required FilmFilter filter, required double intensity})`, `Future<void> suspend()`, `Future<void> resume()`, `dispose()`.
- 캡처 실패는 예외와 `errorMessage`로 전달하고 진행 상태를 복구한다. 중복 촬영 요청은 거부한다. 프런트엔드는 반환 결과 확인 후 저장 성공을 안내한다.
- 프런트엔드가 앱 수명주기를 감시해 `suspend()`와 `resume()`를 호출한다. backend는 요청 경합과 자원 해제를 안전하게 처리한다.

### 미리보기와 저장의 동일 합성

- 촬영 영역은 이미지 비율에 맞춘 세로 5:6이다. 원본을 방향 보정한 뒤 중앙에서 `BoxFit.cover`에 해당하는 방식으로 잘라 사용한다.
- PNG 역시 같은 영역을 `cover`로 채우고 원래 알파에 선택 강도를 곱해 source-over 합성한다. 기본 강도는 1.0이며 0~1 범위로 제한한다.
- 프런트엔드는 같은 5:6 영역에서 카메라 원본을 중앙 cover로 표시하고 선택 PNG를 `Image.asset(fit: BoxFit.cover)`와 강도로 겹친다.
- backend는 촬영 순간 필터와 강도를 고정한다. 원본 필터에서는 PNG를 합성하지 않는다.
- 실제 카메라의 방향·미리보기 크기·전면 반전 차이는 기기별로 확인한다. 필요하면 공통 계산 함수를 합의해 사용한다.

## 검증 기준과 남은 위험

backend는 로직 구현, frontend는 화면 연동과 파일 포맷을 완료했다. tester는 최종 통합 분석, 자동 테스트 16건과 Android 디버그 APK 빌드 통과를 보고했다. 실제 기기 촬영과 앨범 저장 확인은 아직 완료되지 않았다.

- 원본과 필터를 전환하고 투명 PNG 질감이 미리보기와 최종 사진에 반영되는지 확인한다.
- 강도 변경, 촬영 중 중복 요청 방지, 실패 후 상태 복구를 확인한다.
- 기기 앨범 저장과 앱 재시작 후 갤러리 조회를 각각 확인한다.
- 권한 거부, 사진 없음, 읽기 및 저장 실패, 앱 백그라운드 전환과 복귀를 확인한다.
- tester는 `dart format`, `flutter analyze`, `flutter test`와 가능한 Android 빌드 결과를 보고한다.
- 자동 테스트 성공만으로 실기기 카메라, 이미지 방향과 앨범 저장 검증을 완료 처리하지 않는다. Windows에서는 iOS 빌드와 실기기 검증이 제한될 수 있다.
- `.codex/agents/`의 모델 설정은 요청대로 유지하되 이번 실행 도구가 `gpt-5.5` 선택을 제공하지 않으므로 실제 팀 실행 모델은 상위 세션을 상속한다.
- 기기 앨범 저장 성공 후 앱 메타데이터 확정이 실패하면 부분 저장 상태가 발생할 수 있다. 구현은 사본을 보존하고 명시적 오류를 전달하므로 단순 성공으로 숨기지 않는다.

## 통합 검증 중 발견 사항

- `flutter analyze --no-pub`는 문제 없음으로 통과했다.
- 최초 전체 테스트 16건 중 15건은 통과하고 갤러리 재시도 1건은 실패했다. 원인은 갤러리 `_reload`의 `setState` 콜백이 Future를 반환하는 assertion이었다. frontend가 동기 블록 콜백으로 수정한 뒤 tester가 전체 16건 통과를 확인했다.
- 최종 정적 분석과 자동 테스트는 통과했다. 구성은 이미지 합성 4건, 사진 저장소 3건, 카메라 세션 4건, 화면 상호작용 5건이다.
- 자세한 테스트 범위, 발견 결함과 실행 결과는 `docs/test_report.md`에 기록한다.
- 모바일 기기는 연결되지 않았다. 개발 환경 검사에서 일부 Android 라이선스 경고가 있었으나 실제 빌드에서는 이미 수락된 라이선스로 Android SDK Platform 35가 자동 설치되어 라이선스 차단은 확인되지 않았다.
- 최초 Android 디버그 빌드는 앱의 `WRITE_EXTERNAL_STORAGE` 최대 SDK 29와 camera 플러그인의 28이 충돌해 매니페스트 병합에서 실패했다. backend는 tools 네임스페이스와 `tools:replace="android:maxSdkVersion"`를 추가해 앱의 API 29 범위를 유지하도록 수정했다. 이후 tester의 재빌드는 138.7초 만에 성공했고 `build/app/outputs/flutter-apk/app-debug.apk`를 생성했다.
- 테스트 화면 이미지는 Ahem 테스트 글꼴을 사용하므로 레이아웃 확인 근거로만 사용한다. 실제 기기 글꼴 가독성, 미리보기와 저장 사진의 방향 및 색감은 별도 확인이 필요하다.

### 확정 인터페이스와 표시 계약

- `CameraSession`은 `canSwitchCamera`, `isSwitchingCamera`, `isFrontCamera`, `canCapture`와 `pendingSaves`를 제공하고 `Future<void> switchCamera()`를 추가한다.
- `capture`는 선택 인자 `double frameAspectRatio = 5 / 6`을 받는다. 기본값은 기존 호출 호환용이고 새 UI는 실제 전체 화면 사진 영역의 너비/높이 비율을 전달한다.
- `isCapturing`은 `takePicture`와 원본 바이트 취득 동안만 true다. 취득이 끝나면 다음 촬영이 가능하지만 큐 상한과 다른 카메라 상태를 함께 반영한 `canCapture`로 버튼 활성화를 결정한다.
- `capture`의 `Future<SavedPhoto>`는 실제 합성과 기기 앨범 저장 완료 후 완료된다. 각 Future의 오류를 처리하고 취득 피드백과 저장 성공 안내를 구분한다.
- UI는 이번 참고 화면에 맞춰 강도를 1로 고정하고 이전 슬라이더를 제거했다. 촬영 시 햅틱과 90ms 플래시를 제공하며 저장 성공 안내는 각 Future가 완료된 뒤에만 표시한다.
- `pendingSaves`는 취득한 뒤 저장 중인 작업 수를 뜻한다. 센서 취득까지 포함한 미완료 사진은 최대 3장으로 제한하고 이미지 합성·저장은 직렬 처리한다. 단순히 무제한 Future를 시작하는 방식으로 속도를 개선하지 않는다.
- 저장 대기 중 렌즈 전환은 허용하되 센서 취득이나 초기화·다른 전환 중에는 거부한다. 선택 렌즈는 백그라운드 복귀에도 유지한다.
- 전면 미리보기의 기본 거울 표시와 저장을 맞추기 위해 전면 사진은 필터 합성 전에 수평 반전한다. 실제 플러그인 방향·거울 동작은 실기기 확인이 필요하다.
- 필름 목록은 원본, light, cold이며 예시 이미지 경로 상수를 필터 모델에서 제공한다. 선택 버튼은 예시 사진 위에 해당 PNG를 원래 알파로 합성한다. 썸네일은 1:1 영역을 사용할 수 있다.

### 전체 화면 구도와 속도 기준

- 이전 5:6 저장을 유지한 채 화면만 확대하면 저장 사진과 보이는 구도가 달라진다. 메인은 전체 화면 요구를 우선해 출력 비율도 실제 뷰포트 비율로 바꾸도록 결정했다.
- 사진 원본을 해당 비율로 중앙 자르고 PNG 역시 같은 영역에 cover로 합성한다. 격자와 조작 UI는 저장 사진에 포함하지 않는다.
- 촬영 시 필터·강도·비율·렌즈 정보를 고정하고 저장 중 설정을 바꿔도 기존 작업의 결과를 바꾸지 않는다.
- backend는 `lib/services/photo_processor.dart`에 영구 이미지 처리 isolate와 두 PNG의 디코딩 캐시를 구현하고 초기화 시 미리 준비하되 화면 진입을 막지 않도록 구성했다. 큐 상한, 처리 완료 후 메모리 해제와 앱 종료·취득 경합을 함께 검증한다.
- 측정용 `lastCaptureDuration`은 센서 촬영과 바이트 취득 시간, `lastSaveDuration`은 합성과 저장 시간을 구분해 제공한다. 실제 측정값을 확인하기 전 지연 제거를 단정하지 않는다.
- 빠른 취득 피드백은 실제 기기 지연을 제거했다는 뜻이 아니다. 성능 개선은 구조 변경과 실기기 측정을 구분해 보고한다.

### 완료 검증과 위험

- 전후면 전환 후 촬영, 전환 불가 기기, 촬영 중 전환 요청, 앱 복귀 렌즈 유지와 dispose 경합을 검사한다.
- 여러 촬영의 순서, 최대 3장 제한, 필터·강도·렌즈 고정, 저장 실패 후 큐 회복과 각 Future의 오류 처리를 검사한다.
- 새 에셋 로딩, 서로 다른 필름 썸네일, 선택 표시, 전체 화면 비율의 저장 결과와 격자 비저장 여부를 검사한다.
- 이전 검증 16건과 APK 성공은 이번 변경의 완료 근거로 재사용하지 않는다. 새 최종 결과는 tester 보고 후 갱신한다.

### 구현 보고와 검증 대기 상태

- backend는 기존 모델·카메라 제어·합성 코드 및 에셋 등록을 수정하고 `photo_processor.dart`를 추가했다. `flutter pub get`, 관련 파일 포맷과 backend 정적 분석 통과를 보고했다.
- frontend는 `camera_screen.dart`, `camera_viewfinder.dart`, `film_filter_selector.dart` 세 파일만 수정했다. 전체 화면 미리보기와 3×3 격자, 28% 검정 반투명 패널, 흰색 선택 라벨의 굵은 검정 글자, 필름 적용 썸네일, 큰 흰색 촬영 버튼과 갤러리·전환 버튼을 구성했다.
- frontend는 0 크기 방어와 방향 잠금 순서를 유지했고 관련 파일 포맷 및 화면 영역 정적 분석 통과를 보고했다.
- 이전 기본 구현 검증 16건과 이후 0 크기 시작 화면 회귀 수정의 17건 통과는 과거 이력이다. 이번 변경은 tester의 새 실행에서 정적 분석 문제 없음, 자동 테스트 24건 모두 통과, Android 디버그 APK 빌드 성공을 확인했다.
- 이번 최종 분석은 13.8초, 자동 테스트 실행은 약 3초, APK 빌드는 28.1초였다. APK 크기는 187,681,206바이트이며 이 시간은 실제 촬영 지연 측정값이 아니다.
- 테스트 파일 포맷 검사는 9파일에서 변경 없음으로 통과했다. 초기 테스트의 미종료 타이머는 화면 안정화 대기를 추가해 해결했으며 운영 코드의 새 결함으로 보고하지 않았다.
- 최종 APK의 에뮬레이터 설치·카메라 전환·촬영 확인은 메인 에이전트가 진행한다. 실제 휴대폰 성능과 iOS 검증을 대체하지 않는다.
- 메인의 화면 검토 후 frontend가 하단 조작부를 더 작게 조정했다. 썸네일 높이 82→56, 너비 66→52, 촬영 버튼 84→72로 줄이고 흰 필터 라벨은 패널 위에 분리했다. 360×640 기준 패널은 높이 156, 하단 안전 여백 34가 있으면 180이다. 패널 검정 알파 28%는 유지한다. 관련 포맷과 분석 및 아래 추가 회귀 검증을 통과했다.
- 축소 후 최종 재검증은 분석 문제 없음(4.6초), 자동 테스트 25건 모두 통과(약 3초), Android APK 빌드 성공(25.6초)이다. 새 회귀 1건은 360×640의 하단 안전 여백 0·34에서 패널 높이가 화면의 1/3보다 작고 알파 28%임을 확인한다. 24건 통과는 축소 전 이력이며 현재 최종 수는 25건이다.

### 메인 에이전트의 에뮬레이터 확인

- 기존 에뮬레이터는 메모리 부족 종료와 저장 공간 부족 설치 실패가 발생했다. 이후 메모리 4GB 및 별도 QA userdata 이미지로 실행 환경을 구성했다. 초기 설치 실패 후 Flutter의 자동 앱 제거·재설치 시도가 있었으므로 기존 테스트 앱 내부 데이터 보존은 보장할 수 없다. AVD 전체 초기화는 수행하지 않았다. 이 환경 문제를 Flutter 예외나 앱 결함으로 단정하지 않는다.
- 최종 화면 `build/camera_ui_final.png`는 720×1280이며 하단 패널 높이는 약 26.6%였다. 라벨의 패널 위 분리, 실제 예시 사진과 필름 합성 썸네일 3종, 실행 중 예외 없음을 확인했다.
- 하단 축소 이전의 동일 backend로 전면·후면 전환을 각각 1회 확인했다. 콜드 필터 사진이 MediaStore에 720×1280으로 저장되고 앱 썸네일에도 표시됨을 확인했다.
- 해당 디버그 에뮬레이터의 1회 측정은 센서 취득 2.513초, 합성과 저장 7.339초였다. 즉시 완료를 보장하는 결과가 아니며 취득 후 UI 잠금을 풀고 저장을 백그라운드로 분리한 구조가 개선 사항이다. 실제 휴대폰 측정값은 아니다.
- 최종 축소 APK에서 첫 사진의 저장 대기 수가 1인 동안 추가 촬영을 수행했다. MediaStore ID 38과 39로 두 사진이 모두 720×1280으로 저장되었고 앱 갤러리에는 최종 4장이 표시되었다. `build/gallery_final.png`를 확인했으며 Flutter 오류 로그는 없었다.
- 워밍 후 추가 촬영의 디버그 에뮬레이터 측정은 센서 1.566초, 합성과 저장 3.772초였다. 초기 2.513초·7.339초와 함께 환경 참고값으로만 보고하며 물리 기기의 속도 보장으로 사용하지 않는다.
- QA용 분리 ABI APK에서 일반 APK로 바꿀 때도 versionCode 4001→1에 따른 재설치로 별도 QA 이미지의 앱 사본이 초기화되었다. 이후 최종 앱에서 촬영·저장을 다시 검증했다.

## 줌·촬영 설정·동영상 확장

### 목표와 범위

- 두 손가락 핀치로 렌즈의 지원 범위 안에서 카메라 줌을 조절한다.
- 설정 하단 시트에서 격자와 수평계를 각각 켜고 끈다. 수평계는 흰 고정 기준선과 회전선을 구분하고 오차가 ±2도 이내이면 노란색으로 표시한다.
- 사진의 16:9, 4:3, 1:1 비율을 선택한다. 세로 화면은 각각 9:16, 3:4, 1:1 사진 영역을 중앙에 표시하고 남는 공간은 검정으로 채운다.
- 동영상 버튼을 실제 녹화 시작·정지·기기 앨범 저장에 연결하고 앱 갤러리에서 재생한다.
- 영상 필터 합성은 이번 요청에 포함하지 않는다. 동영상은 원본으로 녹화한다고 UI에 표시하며 영상 모드에서 필터 선택을 비활성화한다. 사진은 기존 필터 합성을 유지한다.
- 사진 화면 진입 시 마이크 권한을 요청하지 않는다. 소리를 포함한 영상 모드 진입 때 필요한 권한을 요청하고 거부·제한 상태를 처리한다.

### 확정 연동 계약

- 초기 설정은 격자 켜짐, 수평계 꺼짐, 사진 16:9(세로 사진 영역 9:16)다.
- `CameraSession` 줌: `minZoom`, `maxZoom`, `currentZoom`, `Future<void> setZoom(double)`.
- 동영상 상태: `videoMode`, `isRecording`, `isRecordingBusy`, `canStartRecording`.
- 동영상 동작: `setVideoMode(bool)`, `startVideoRecording()`, `stopVideoRecording()`이며 정지 결과는 `Future<SavedPhoto>`다. `lastSavedVideo`로 백그라운드 전환 중 자동 저장된 영상도 UI에 전달한다.
- `SavedPhoto.isVideo`는 기본 false이며 기존 JSON도 사진으로 읽는다. `isInDeviceAlbum`은 기본 true로 이전 메타데이터와 호환한다. 영상 앨범 저장 실패 시 사본을 보존할 수 있으나 false 상태를 전달해 UI가 앨범 저장 성공으로 안내하지 않게 한다. `PhotoRepository.saveVideo({required String path})`로 영상을 보관하고 `listPhotos()`는 사진과 영상을 함께 반환한다. 기존 이름은 호출 호환을 위해 유지한다.
- `LevelController extends ChangeNotifier`는 `enabled`, `isAvailable`, nullable `angleDegrees`, `setEnabled`, `suspend`, `resume`, `dispose`를 제공한다. 센서 스트림은 테스트용 주입을 지원한다.
- backend가 `sensors_plus`, `video_player` 의존성을 등록하고 frontend가 영상 뷰어를 연결한다. 컨트롤러의 정확한 파일 경로는 구현 역할끼리 직접 공유한다.
- 영상 미리보기는 세로 9:16 원본 프레임을 검정 여백 안에 표시한다. 사진 비율 설정과 별도로 다루고 강제 사진 자르기를 영상에 적용하지 않는다.
- 사용자는 메인의 선택 질문에 원본 동영상·소리·앨범 저장을 확정했다. 영상 필터 합성은 포함하지 않으며 영상 모드에서 사진 필터를 숨기거나 비활성화한다.

### 공통 동작과 안전한 경합 처리

- 줌 최소·최대값은 렌즈 초기화마다 다시 읽고 범위를 제한한다. 빠른 핀치 입력은 모든 요청을 쌓지 않고 최신값으로 합치며 카메라 변경·해제와 충돌하지 않게 한다.
- 두 손가락을 사용한 확대·축소만 줌에 반영하고 한 손가락 조작이 촬영이나 설정을 방해하지 않게 한다.
- 선택 비율의 실제 사진 영역 비율을 기존 `frameAspectRatio`로 전달한다. 필터와 격자·수평계는 사진 영역 안에만 표시하고 UI 선은 저장 이미지에 포함하지 않는다.
- 수평계는 센서 미지원·스트림 오류와 바닥을 향한 평평한 자세를 유효한 0도로 취급하지 않는다. 유효하지 않으면 중립 상태와 필요한 안내를 표시한다. 토글·백그라운드 전환·화면 종료 때 구독을 해제한다.
- 녹화 중 렌즈·모드 전환 및 정지 중 중복 요청을 제한한다. 백그라운드 전환 때 가능하면 녹화를 안전하게 멈추고 저장하며 실패를 성공으로 숨기지 않는다.
- 영상은 네이티브 원본 비율·방향으로 저장한다. 사진 비율 옵션을 영상에 조용히 적용하거나 영상이 필터 합성되었다고 안내하지 않는다.
- 기존 사진 메타데이터는 기본 사진으로 읽을 수 있어야 한다. 사진과 영상의 파일 확장자·종류를 구분해 갤러리에서 적절한 뷰어를 연다.

### 구현 보고와 통합 검증 현황

- backend는 카메라 세션의 줌과 녹화 상태, 오디오 모드 재초기화 및 백그라운드 정지·저장을 구현했다. `level_controller.dart`는 약 100ms 센서 구독, 세로 회전각 계산, 평평한 자세·오래된 값·센서 오류 무효 처리와 구독 취소를 제공한다.

- frontend는 핀치, 설정 시트, 비율 레터박스, 수평계, 녹화 타이머·시작/정지, 원본 안내, 영상 갤러리 표시와 `video_player` 상세 화면을 연결했다. 재생 화면은 로딩·오류·재시도·재생/정지·탐색과 수명주기 정지를 처리한다.
- 최초 통합 테스트는 37건 중 35건 통과했다. 실제 시작 화면의 24px 오버플로는 frontend가 수정 중이며, 이전 전체 뷰포트 비율을 기대한 테스트 1건은 새 기본 9:16 요구에 맞게 tester가 수정한다. 두 원인을 운영 결함과 테스트 기대값 변경으로 구분한다.

### 메인의 네이티브 에뮬레이터 검증

- 설정 버튼을 열어 격자 끄기, 수평계 켜기와 정사각형 선택이 실제 화면에 반영됨을 확인했다.
- 에뮬레이터 가속도 `0:9.8:0`을 주입해 노란 수평 상태를, `2:9.6:0`을 주입해 약 12도 기울기와 흰 고정선·회전선의 차이를 확인했다. 캡처는 `build/camera_level_aligned.png`, `build/camera_level_tilted.png`다. 실제 센서 정밀도 측정은 아니다.
- 실제 사진 세 비율이 MediaStore에 JPEG로 저장됨을 확인했다. ID 35는 720×720(1:1), ID 37은 720×960(세로 4:3), ID 38은 720×1280(세로 16:9)이다.
- 사진 모드에서는 `RECORD_AUDIO`가 허용되지 않은 상태였고 영상 모드 진입에서만 마이크 허용 창이 표시되었다. 허용 뒤 실제 네이티브 녹화·타이머·정지와 기기 앨범 MP4 저장이 성공했다.
- 저장된 영상은 MediaStore ID 36, 1280×720, 약 30.564초이며 파일 파싱에서 영상 `vide/avc1`과 소리 `soun/samr` 트랙이 모두 존재했다. 에뮬레이터가 오디오 출력 없이 실행되어 실제 음성 품질은 검증하지 않았다.
- 혼합 갤러리의 영상 표시와 실제 `VideoPlayer` 재생 진행·일시정지 아이콘을 확인했다. 캡처는 `build/video_recording.png`, `build/video_playing.png`, `build/media_gallery.png`다.
- 줌을 지원하는 전면 렌즈에 네이티브 API로 약 12.932배를 적용한 뒤 1배 복귀와 현재값을 확인했다. 기본 가상 장면 후면 렌즈의 최대 1배는 해당 하드웨어 제한이다. 메인의 호출은 VM을 통한 실제 카메라 API 확인이고 두 손가락·한 손가락 구분은 위젯 테스트 근거로 구분한다.
- 해당 실행에서 Flutter 오류 로그는 없었다. 물리 기기의 줌, 센서 정확도와 음성 품질, 기기별 영상 방향·성능 및 iOS 확인은 남아 있다.

- 0.6배는 실제 하드웨어 지원 때만 제공한다. 미지원 기기는 실제 최소 배율을 표시하고 가짜 광각 화면을 만들지 않는다. 최대 100배 중 네이티브 범위를 넘는 부분은 디지털 자르기이며 화질 제한을 안내한다.
- 이전 원본 영상 전용 정책은 이번 명시적 필터 요청으로 확장한다. 이전 자동 테스트 47건과 APK 결과는 새 기능의 완료 근거로 재사용하지 않는다.

project_manager는 생산 코드를 수정하거나 에이전트를 생성하지 않는다. 네이티브 등록 지점의 충돌은 메인이 조율한다. 기존 미커밋 기능과 사용자 데이터를 보존하고 요청하지 않은 Git 커밋·푸시는 수행하지 않는다.

### 확정 Dart 계약

- `currentZoom`은 논리 요청값을 즉시 반영한다. `minZoom = max(0.6, nativeMin)`, `maxZoom = 100`이며 렌즈 변경 때 지원 범위를 갱신한다.
- `previewDigitalZoom >= 1`, `nativeMaxZoom`, `isDigitalZoom`을 제공한다. 네이티브 호출은 직렬로 최신값을 합치고 실패와 적용 상태를 숨기지 않는다.
- 사진은 하드웨어 줌과 추가 디지털 자르기를 결합한다. 촬영 순간 필터·강도·비율과 디지털 배율을 고정하고 최종 이미지에 실제 반영한다.
- `startVideoRecording`은 선택 인자 `FilmFilter filter`(기본 원본)와 `double intensity`(기본 1)를 받아 선택 필터를 고정한다. `isVideoProcessing`으로 출력 중 상태를 제공하며 `isRecordingBusy`는 기존 전체 잠금 역할을 유지한다.
- 영상은 녹화 시작 전 네이티브 기준 줌을 `minZoom`에 고정하고 녹화 중 핀치는 소프트웨어 키프레임만 기록한다. 네이티브 적용 시점과 영상 프레임의 차이를 피하면서 원본에 적용된 기준 줌을 출력 단계에서 다시 적용하지 않는다.
- 필터 강도는 Dart에서 PNG 알파를 미리 조정해 전달한다. `VideoProcessor`는 테스트 주입을 지원한다.

### 네이티브 출력 계약

- 채널은 `aeroll/video_effects`, 메서드는 `exportVideo`다.
- 인자는 `inputPath`, `outputPath`, nullable `overlayPath`, `zoomKeyframes: [{timeMs, digitalScale}]`다. 성공 시 완성된 출력 경로를 반환하고 실패는 명시적 오류를 전달한다.
- 시간은 녹화 시작 기준 밀리초이며 키프레임에는 추가 디지털 배율만 포함한다. 원본에 이미 반영된 네이티브 기준 줌을 중복 적용하지 않는다.
- Android Media3와 iOS AVFoundation으로 중앙 자르기·PNG 원래 알파 source-over 합성을 수행한다. 필터는 확대된 카메라 프레임 뒤에 고정 크기로 합성하고 소리 트랙·표시 방향·시간을 유지한다.
- 외부 FFmpeg 실행 파일 배포에 의존하지 않는다. 실제 출력 파일이 완성된 뒤 기기 앨범에 저장하고 출력 실패 시 원본을 필터 성공으로 저장하지 않는다.

### UI와 검증 기준

- 소프트웨어 미리보기 확대는 원본 카메라에만 적용하고 필름·격자·수평계·조작부는 함께 확대하지 않는다.
- 세로 눈금과 현재 배율은 줌 상호작용 중 표시한다. 마지막 제스처 후 2초 뒤 페이드하며 새 제스처는 숨김 예약을 취소한다. 화면 종료 때 타이머·애니메이션 자원을 정리한다.
- 영상 모드에서 녹화 전 필터를 선택할 수 있지만 녹화 중 선택 변경은 잠근다. 녹화 정지, 출력 처리, 앨범 저장 완료를 구분해 안내한다.
- 지원·미지원 0.6배, 기본 1배, 상한 100배, 빠른 핀치·렌즈 변경·실패 복구, 눈금 2초 경계·재진입·종료를 검사한다.
- 사진과 실제 영상 파일의 디지털 구도·필터 픽셀 변화, 녹화 중 줌 키프레임, 음성 트랙·방향·재생, 출력 실패 시 성공 안내 금지를 확인한다.
- 100배는 광학 성능 보장이 아니다. 기기별 광각 지원, 디지털 화질 저하, 출력 처리 시간과 발열·메모리, iOS 및 실기기 검증 여부를 정직하게 보고한다.

### 구현 보고와 검증 진행 상태

- backend는 `video_processor.dart`, `zoom_keyframe.dart`를 추가하고 카메라 세션과 사진 합성·처리·저장소를 수정했다. Dart 구현·관련 분석은 완료했으나 네이티브 실제 출력 완료와는 구분한다.
- frontend는 `zoom_ruler.dart`를 추가하고 카메라·영상 상세 화면, 미리보기·설정 시트를 수정했다. 현재 배율을 즉시 표시하는 연결 눈금, 마지막 제스처 2초 뒤 300ms 페이드, 타이머 취소와 수명주기 정리를 구현했다.
- 미리보기는 원본 카메라만 확대하고 PNG·격자·수평계는 고정한다. 영상 필터 선택은 녹화 전에 허용하고 녹화·출력 중에는 잠근다. 출력 진행 상태와 실제 저장 필터 이름도 표시한다.
- frontend는 수정·생성한 5개 파일 포맷과 화면 영역 분석 문제 없음을 보고했다. 작업 중 문자열 인코딩 손상을 발견해 UTF-8로 복구하고 재분석했다.
- 네이티브 역할은 Android/iOS 코드를 작성했고 Android 컴파일을 진행한다. Windows 환경의 iOS 빌드·출력은 확인되지 않았다.
- 기존 47건을 다시 실행한 초기 결과는 46건 통과, 원본 영상 정책을 기대한 1건 실패였다. 이는 새 필터 요구에 맞춰 기대값을 갱신하는 중이며 새 회귀도 추가한다. 최종 분석·테스트 수와 APK·출력 성공은 아직 확정하지 않는다.
- 메인은 영상 픽셀·소리·방향 검증용 `imageio-ffmpeg`를 `build/qa_tools`에만 설치하고 별도 작업 공간 QA 에뮬레이터를 준비했다. 해당 도구는 제품 실행 의존성이 아니다.

### 최신 자동 검사와 실제 출력 비교

- 최종 `flutter analyze --no-pub`는 문제 없음(1.7초), `flutter test --no-pub`는 64건 모두 통과(약 7초)했다. 테스트 포맷은 17파일 변경 없음이다. 기존 47건에 디지털 줌 7건·영상 처리기 7건·눈금 UI 3건을 추가했다.
- 최초 전체 APK는 39.9초에 성공했다. 이후 네이티브 알파 수정 후 Kotlin 컴파일 약 16초, 최종 일반 APK 19.4초에 성공했고 크기는 191,776,440바이트다. 빌드 시간은 영상 출력 처리 시간과 구분한다.
- 실제 Dart 결함은 에셋 읽기 실패 시 복구 작업 명세가 누락되던 문제였다. backend가 에셋 처리 전 입력·출력·타임라인·필터·강도·단계를 선기록하고 준비 완료 뒤 원자 갱신하도록 수정했다. 읽기 실패와 잘못된 PNG 모두 회귀 통과했다.
- 실제 Android 결함은 premultiplied RGB에 오버레이 셰이더가 알파를 다시 곱해 필름이 어두워지던 문제였다. 네이티브 역할이 straight-alpha RGBA로 복원해 수정했다.
- 수정 후 실제 네이티브 출력의 1·2·4·100배 평균 픽셀 오차는 Pillow 기준으로 각각 3.834·2.833·1.430·1.290이었다(채널 범위 0~255, 수정 전 27.643). 해당 테스트 영상의 결과이며 모든 기기의 화질 보장은 아니다.
- 90도 회전 메타데이터가 있는 영상은 240×320으로 출력되어 표시 방향이 유지되었다. 테스트 오디오 3.019초·약 440.27Hz·RMS 2884.55도 유지되었으나 실제 목소리 품질 검증은 아니다.
- 실제 눈금 화면 `build/zoom_ruler_100_visible.png`에서 100배 표시를 확인했다. 핀치 종료 직후·1.9초·2.4초의 표시 상태는 true·true·false로 확인했고 100배 사진의 실제 MediaStore 저장과 갤러리 썸네일도 확인했다.
- 실제 앱에서 콜드 선택→37.432초 녹화→정지→네이티브 합성→MediaStore ID 36의 1280×720 MP4 저장 완료를 확인했다. 완료 시 `isVideoProcessing=false`, 오류는 null이었다.
- 앱 갤러리의 영상 항목을 열어 상세 화면의 콜드 영상 라벨, 필터 색과 세로 표시 방향을 눈으로 확인했다. 산출물은 `build/filtered_video_gallery.png`, `build/filtered_video_playback.png`다. 이는 별도 픽셀 기준 영상 검사와 구분되는 앱 전체 경로의 성공 근거다.
- 이번 Android 검증은 완료했지만 실제 광각 지원 기기의 0.6배, 100배 디지털 화질, 물리 기기 음성 품질·출력 성능·발열과 iOS 빌드·출력은 별도 확인이 남는다. 녹화 정지 후 출력 처리 시간을 실제 저장 완료와 혼동하지 않는다.
